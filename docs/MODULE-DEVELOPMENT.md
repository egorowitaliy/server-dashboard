# Разработка модулей Server Dashboard

## 1. Для чего нужны внешние модули

Внешний модуль добавляет функции, которые нужны не каждому серверу и поэтому не должны становиться частью ядра Server Dashboard. Это может быть контроль резервных копий, телефония, локальный сервис, специализированный датчик, состояние внутренней очереди или любая другая функция конкретной инфраструктуры.

Главное правило: для подключения модуля не нужно менять `index.php`, `api.php`, `app.js`, `protocol.py` или исходный код привилегированной службы. Модуль устанавливается в отдельный каталог, явно включается в конфигурации и регистрирует только свои операции и элементы интерфейса.

API модулей версии 1 состоит из двух частей:

- Python API для серверной части;
- `window.Dashboard` для браузерной части.

## 2. Минимальная структура

```text
my-module/
├── manifest.toml
├── backend.py
├── config.toml
└── public/
    ├── module.js
    └── module.css
```

`config.toml` необязателен. CSS также необязателен и нужен только для специфичного содержимого, которому недостаточно штатных компонентов интерфейса.

Каталог модуля обычно размещается так:

```text
/opt/server-dashboard-extensions/my-module/
```

В основном конфиге:

```toml
[extensions]
root = "/opt/server-dashboard-extensions"
enabled = ["my-module"]
```

## 3. Идентификатор модуля

Идентификатор:

- должен совпадать с именем каталога;
- используется в именах операций и в браузерном API;
- не должен совпадать с идентификатором встроенного модуля;
- должен оставаться неизменным между совместимыми версиями.

Для операций внешнего модуля рекомендуется пространство имён:

```text
ext.<module-id>.<operation>
```

Например:

```text
ext.my-module.state
ext.my-module.restart
```

## 4. manifest.toml

Пример:

```toml
api = 1
id = "my-module"
name = "Мой модуль"
version = "1.0.0"
icon = "activity"
order = 90
page = false
placements = ["system"]

[backend]
entrypoint = "backend.py"

[assets]
css = "module.css"
js = "module.js"
```

### Поля верхнего уровня

| Поле | Назначение |
| --- | --- |
| `api` | Версия API модулей. Для текущей версии должно быть `1`. |
| `id` | Постоянный идентификатор модуля. |
| `name` | Название для интерфейса и диагностики. |
| `version` | Версия самого модуля. |
| `icon` | Имя значка из набора Server Dashboard. |
| `order` | Порядок относительно других модулей. |
| `page` | `true`, если модуль создаёт отдельную страницу в меню. |
| `placements` | Список точек, куда модуль добавляет свои блоки. В версии API 1 доступны `overview` и `system`. |

Если `page = true` или указан хотя бы один элемент `placements`, модуль должен объявить JavaScript-файл в `[assets]`. При необходимости можно добавить один CSS-файл:

```toml
[assets]
js = "module.js"
css = "module.css"
```

Оба файла должны находиться непосредственно в каталоге `public/`.

Описание проверяется строго. Неизвестное поле, неверный тип, отсутствующий файл или конфликт идентификатора приводят к отказу загрузки модуля.

## 5. Конфигурация модуля

Если рядом с `manifest.toml` есть `config.toml`, загрузчик разбирает его и передаёт серверной части через `context.config`.

Не храните в таком файле секреты, если они не должны быть доступны всему привилегированному процессу. Для модуля, которому нужны собственные секреты, лучше отдельно спроектировать файл с ограниченными правами и явно документировать его расположение.

## 6. Серверная часть

`backend.py` должен экспортировать:

```python
def register(registry, context):
    ...
```

`registry` — ограниченный объект регистрации текущего модуля. Это не внутренний реестр Server Dashboard. Он позволяет регистрировать операции только от имени текущего модуля.

`context` содержит:

- `context.id` — идентификатор;
- `context.root` — каталог модуля;
- `context.config` — содержимое `config.toml`;
- `context.dashboard_config` — основная конфигурация Server Dashboard.

### Простая операция чтения

```python
from server_dashboard.module_api import OperationSpec, no_params


def read_state():
    return {
        "status": "ok",
        "value": "Работает",
    }


def register(registry, context):
    registry.register_operation(
        OperationSpec(
            name="ext.my-module.state",
            kind="read",
            module_id=context.id,
            validator=no_params,
            handler=lambda dashboard_config, params: read_state(),
        )
    )
```

### Параметры операции

Для простого набора строк можно использовать штатный валидатор:

```python
from server_dashboard.module_api import exact_string_params

validator = exact_string_params(
    ("target",),
    max_length=64,
)
```

Для своей структуры напишите функцию, которая принимает словарь `params` и при ошибке выбрасывает `DashboardOperationError`.

```python
from server_dashboard.module_api import DashboardOperationError


def validate(params):
    if set(params) != {"enabled"}:
        raise DashboardOperationError(
            "invalid_params",
            "Ожидается параметр enabled",
        )

    if not isinstance(params["enabled"], bool):
        raise DashboardOperationError(
            "invalid_params",
            "enabled должен быть true или false",
        )
```

### Структурированные ошибки

Для ожидаемой ошибки используйте:

```python
raise DashboardOperationError(
    "not_ready",
    "Служба ещё не готова",
)
```

Код и сообщение дойдут до веб-части как ошибка операции. Не используйте исключение для штатного успешного состояния.

### Операции изменения

Для действия укажите `kind="action"`:

```python
OperationSpec(
    name="ext.my-module.restart",
    kind="action",
    module_id=context.id,
    validator=exact_string_params(("target",), max_length=64),
    handler=restart_target,
)
```

Такая операция вызывается через `/api/action`. Веб-часть требует действующую сессию и CSRF, а результат действия попадает в журнал.

### Что нельзя передавать напрямую в системную команду

Не принимайте из браузера:

- путь к исполняемому файлу;
- произвольную командную строку;
- свободный список аргументов;
- имя systemd unit, контейнера или файла без собственного списка разрешений.

Правильная схема: браузер передаёт небольшой идентификатор, серверная часть проверяет его по заранее известному набору и сама строит фиксированный вызов.

## 7. Ответ операции

Результат должен быть пригоден для JSON: словари, списки, строки, числа, `true`/`false` и `null`.

Не возвращайте объект `Path`, `set`, открытый файл, исключение или произвольный экземпляр класса. Служба ограничивает размер ответа, поэтому также не стоит передавать большие двоичные данные или многомегабайтные тексты через этот API.

## 8. Браузерная часть

Внешний JavaScript получает глобальный объект:

```javascript
const Dashboard = window.Dashboard;
```

Публичный контракт версии 1:

```text
Dashboard.rpc.read()
Dashboard.rpc.action()
Dashboard.ui.root
Dashboard.ui.el()
Dashboard.ui.icon()
Dashboard.ui.panel()
Dashboard.ui.statusNode()
Dashboard.ui.compactRow()
Dashboard.ui.appendAttention()
Dashboard.ui.appendSummary()
Dashboard.format.bytes()
Dashboard.format.duration()
Dashboard.format.dateTime()
Dashboard.modules.registerPage()
Dashboard.modules.registerPlacement()
Dashboard.modules.isEnabled()
Dashboard.modules.meta()
Dashboard.modules.openPage()
```

Не используйте внутренние функции `app.js`, которых нет в этом списке: они не считаются стабильным API.

## 9. Чтение и изменение из браузера

Чтение:

```javascript
const data = await Dashboard.rpc.read(
  "ext.my-module.state"
);
```

Действие:

```javascript
await Dashboard.rpc.action(
  "ext.my-module.restart",
  {target: "example"}
);
```

Браузерная часть не должна самостоятельно обращаться к Unix-сокету, Docker или systemd.

## 10. Отдельная страница

В `manifest.toml`:

```toml
page = true
placements = []
```

В `module.js`:

```javascript
Dashboard.modules.registerPage(
  "my-module",
  async () => {
    const data = await Dashboard.rpc.read(
      "ext.my-module.state"
    );

    const card = Dashboard.ui.panel(
      "Мой модуль",
      "activity"
    );

    card.append(
      Dashboard.ui.compactRow(
        "activity",
        "Состояние",
        data.value,
        data.status
      )
    );

    Dashboard.ui.root.replaceChildren(
      card
    );
  }
);
```

Не создавайте собственную боковую панель, шапку или независимую систему навигации. Оболочкой приложения управляет Server Dashboard.

### Периодическое обновление страницы

Если данные должны автоматически обновляться, зарегистрируйте страницу так:

```javascript
Dashboard.modules.registerPage(
  "my-module",
  render,
  {live: true}
);
```

Ядро будет повторно вызывать обработчик только пока эта страница открыта. Не создавайте бесконечный `setInterval`, который продолжает работать после ухода пользователя на другую страницу.

## 11. Блок на главной странице

В `manifest.toml`:

```toml
placements = ["overview"]
```

Пример:

```javascript
Dashboard.modules.registerPlacement(
  "my-module",
  "overview",
  async ({summaryPanel, attentionPanel}) => {
    const data = await Dashboard.rpc.read(
      "ext.my-module.state"
    );

    Dashboard.ui.appendSummary(
      summaryPanel,
      {
        iconName: "activity",
        label: "Мой модуль",
        status: data.status,
        text: data.value,
        target: null
      }
    );

    if (data.status !== "ok") {
      Dashboard.ui.appendAttention(
        attentionPanel,
        {
          severity: "warn",
          title: "Мой модуль требует внимания",
          message: data.message || "Проверьте состояние модуля.",
          target: null
        }
      );
    }
  }
);
```

В обработчик передаются уже созданные штатные панели. Не заменяйте их целиком и не меняйте структуру главной страницы.

## 12. Блок на странице «Система»

В `manifest.toml`:

```toml
placements = ["system"]
```

Обработчик получает `leftColumn` и `rightColumn`:

```javascript
Dashboard.modules.registerPlacement(
  "my-module",
  "system",
  async ({rightColumn}) => {
    const data = await Dashboard.rpc.read(
      "ext.my-module.state"
    );

    const card = Dashboard.ui.panel(
      "Мой модуль",
      "activity"
    );

    card.append(
      Dashboard.ui.compactRow(
        "activity",
        "Состояние",
        data.value,
        data.status
      )
    );

    rightColumn.append(card);
  }
);
```

## 13. Единый стиль интерфейса

Модуль должен выглядеть как часть Server Dashboard, а не как отдельное приложение, вставленное внутрь страницы.

### Разделение стилей core и extension

`web/public/assets/css/app.css` принадлежит ядру Server Dashboard. Внешний модуль не должен требовать добавления своих CSS-классов, собственных иконок или layout-правил в `app.css`.

Специфичные стили модуля размещаются в:

```text
<extension>/public/module.css
```

и объявляются через:

```toml
[assets]
css = "module.css"
js = "module.js"
```

CSS-классы модуля должны иметь собственное пространство имён. Например, для модуля `my-module`:

```css
.my-module-panel {
  min-width: 0;
}

.my-module-value {
  font-weight: 600;
}
```

Не используйте слишком общие классы вроде:

```text
.card
.row
.item
.title
.active
```

если они не являются штатными классами Dashboard.

Для собственной иконки extension также рекомендуется использовать имя с namespace, например:

```text
my-module-phone
```

и определить mapping в `module.css`:

```css
.i-my-module-phone {
  --mask: url("phone.svg");
}
```

Сам `phone.svg` при этом находится в `public/` этого же extension.

Таким образом, удаление extension должно полностью удалять его JavaScript, CSS и SVG без каких-либо изменений файлов core.


### Используйте штатные компоненты

Для типовых элементов применяйте публичные функции:

- `Dashboard.ui.panel()` — обычная плоская панель;
- `Dashboard.ui.compactRow()` — строка показателя на странице «Система»;
- `Dashboard.ui.statusNode()` — состояние с общей цветовой системой;
- `Dashboard.ui.icon()` — значок из набора Dashboard;
- `Dashboard.ui.appendSummary()` — строка сводки на главной странице;
- `Dashboard.ui.appendAttention()` — запись в блоке «Требует внимания»;
- `Dashboard.format.*` — общие форматы размера, времени и даты.

Не копируйте HTML и CSS встроенной панели вручную, если для неё уже есть функция API.

### Таблицы

Для таблицы используйте штатные классы:

```javascript
const wrap = Dashboard.ui.el(
  "div",
  "table-wrap"
);

const table = Dashboard.ui.el(
  "table",
  "table"
);

wrap.append(table);
```

`table-wrap` обеспечивает такое же поведение на узком экране, как у встроенных страниц.

### Кнопки

Базовый класс — `btn`. Допустимы штатные варианты `btn-primary` и `btn-danger`, если они уже используются в основной теме.

Не задавайте глобальные правила для `.btn`, `.table`, `.panel` и других общих классов.

### Статусы

Используйте те же смысловые состояния, что и ядро:

- `ok` — норма;
- `warn` — требуется внимание, но функция ещё работает;
- `error` — ошибка или недоступность.

Не вводите собственные цвета для тех же смыслов. Например, нормальное состояние не должно быть синим в одном модуле и зелёным в другом.

### Отступы и плотность

Server Dashboard использует компактную административную компоновку. Не добавляйте большие пустые зоны, объёмные карточки, сильные тени и декоративные элементы без функциональной причины.

Для обычной панели достаточно стандартных внутренних отступов, которые задаёт ядро. Модуль должен добавлять собственные отступы только внутри специфичного элемента, например графика или временной шкалы.

### Типографика

Не меняйте глобальный шрифт, размер базового текста и стили заголовков. Текст внутри модуля должен наследовать оформление Dashboard.

Используйте короткие понятные подписи. В интерфейсе лучше писать «Перезапустить», «Состояние», «Последний запуск», а не технические имена методов и внутренние идентификаторы.

### Когда собственный CSS уместен

Свой CSS нужен для содержимого, которого нет в стандартном наборе компонентов, например:

- формы звуковой волны;
- специализированного графика;
- сетки камер;
- визуального редактора;
- сложного просмотрщика данных.

Даже в этом случае ограничивайте селекторы пространством своего модуля, например `.my-module-waveform`, и не переопределяйте оформление всего приложения.

### Что не переопределять

Не задавайте свои правила для:

```text
.topbar
.sidebar
.main
.panel
.table
.btn
.status
```

Не меняйте общие CSS-переменные темы из внешнего модуля.

### Диалог подтверждения

Универсальный диалог пока не является частью API модулей версии 1. Для простого подтверждения можно использовать `window.confirm()`. Если нескольким модулям понадобится одинаковое сложное окно, правильнее сначала добавить общий компонент в публичный API ядра, а не копировать внутреннюю реализацию.

## 14. Значки

`icon` в описании модуля и имена, передаваемые `Dashboard.ui.icon()`/`panel()`/`compactRow()`, должны соответствовать значкам, которые уже предоставляет Server Dashboard.

Если модулю нужен уникальный рисунок, можно подключить свой CSS и статический файл, но для обычных действий лучше использовать существующий набор — так интерфейс остаётся единообразным.

## 15. Адаптивность

Проверяйте модуль как минимум в двух режимах:

- обычный настольный экран;
- узкий мобильный экран.

Панели в точке `system` автоматически переходят в одну колонку вместе с основной страницей. Таблицы помещайте в `.table-wrap`.

Не задавайте жёсткую ширину, из-за которой вся страница становится шире окна.

## 16. Обработка ошибок в браузере

Если операция чтения не удалась, обработчик может выбросить исключение. Ядро перехватывает ошибку точки размещения, пишет сообщение в консоль и, для главной страницы, добавляет предупреждение о недоступном модуле.

Если для вашего интерфейса нужен более точный текст, перехватите ошибку внутри обработчика и покажите понятное состояние в собственной панели.

Не скрывайте ошибку зелёным статусом. Если достоверность данных не подтверждена, состояние должно быть `warn` или `error`.

## 17. Безопасность модуля

Серверная часть выполняется с правами привилегированной службы. Поэтому:

- устанавливать модуль должен администратор;
- каталог и файлы должны принадлежать `root`;
- группа и остальные пользователи не должны иметь право записи;
- символические ссылки в доверенных файлах и каталогах не допускаются;
- вся цепочка каталогов до корня расширений должна проходить те же проверки;
- операция `read` не должна менять систему;
- операция `action` должна иметь строгую проверку параметров;
- секреты нельзя выводить в ответ API или журнал;
- не ослабляйте systemd-ограничения Server Dashboard ради модуля.

Если модулю необходим сетевой клиент, доступ к отдельному устройству или дополнительные права, рассмотрите отдельную службу-посредник с минимально необходимыми полномочиями.

## 18. Совместимость

`api = 1` — версия API модулей. Она не совпадает с версией Server Dashboard или самого модуля.

Стабильными считаются только:

- классы и функции, документированные в `server_dashboard.module_api`;
- свойства `context`, описанные в этом документе;
- свойства `window.Dashboard`, перечисленные выше;
- точки размещения, перечисленные для API версии 1.

Импорт внутренних источников данных ядра, обращение к приватным переменным `app.js` или прямое чтение файлов Server Dashboard не считается стабильным контрактом.

## 19. Проверка перед включением

Минимальный порядок:

1. проверьте синтаксис `manifest.toml` и `config.toml`;
2. проверьте Python-файл через `python3 -m py_compile`;
3. проверьте JavaScript через `node --check`, если Node.js доступен;
4. установите каталог как `root:root` без права записи группе и остальным;
5. добавьте идентификатор в `[extensions].enabled`;
6. выполните `/opt/server-dashboard/scripts/check-config.py`;
7. проверьте `dashboard-rpc modules.list --pretty`;
8. откройте нужную страницу и убедитесь, что модуль не ломает соседние блоки;
9. отдельно проверьте отказ при некорректных параметрах действия.

## 20. Что публиковать вместе с модулем

Для самостоятельного модуля желательно иметь:

```text
README.md
LICENSE
CHANGELOG.md
manifest.toml
config.example.toml
backend.py
public/
tests/
```

В архив и репозиторий не должны попадать локальный `config.toml` с частными путями или секретами, временные файлы, журналы, резервные копии исходников и каталоги `__pycache__`.

## 21. Готовый шаблон

В `docs/examples/module-template/` находится минимальный рабочий пример, который регистрирует операцию чтения и добавляет одну строку на страницу «Система». Его удобнее копировать как основу, чем начинать модуль с пустого каталога.
