# Архитектура Server Dashboard

## Общая схема

Server Dashboard разделён на две части:

1. непривилегированная веб-часть на PHP и JavaScript;
2. привилегированная служба на Python, которая выполняет только зарегистрированные операции.

Связь между ними идёт через Unix-сокет `/run/server-dashboard/dashboard.sock`. Веб-часть не запускает `systemctl`, Docker или Fail2Ban напрямую.

## Почему привилегии вынесены отдельно

Веб-интерфейс должен уметь, например, перезапустить разрешённую службу, но сам PHP-FPM не должен работать от `root`. Поэтому браузер отправляет запрос PHP, PHP передаёт структурированную операцию службе, а служба проверяет её по реестру и только после этого выполняет действие.

Для изменяющих операций дополнительно используются:

- авторизация;
- CSRF-проверка;
- журнал действий;
- списки разрешённых объектов;
- строгая проверка параметров.

## Реестр модулей

`server_dashboard.module_registry` собирает встроенные страницы и включённые внешние модули в единый реестр. В нём хранятся:

- сведения о модуле;
- зарегистрированные операции чтения и изменения;
- статические файлы внешнего модуля;
- ошибки загрузки расширений.

Если встроенный модуль выключен в `[modules]`, его страница не показывается, а операции становятся недоступны. Главная страница также прекращает опрашивать его источники данных.

## Встроенные страницы

В версии 1.0.0 доступны:

- `overview` — общая сводка;
- `services` — службы systemd;
- `docker` — контейнеры;
- `fail2ban` — блокировки;
- `system` — хранилища, SMART и расписание;
- `docs` — локальная документация;
- `audit` — журнал действий.

Компоненты `storage`, `smart` и `schedule` внутри страницы «Система» отключаются независимо.

## Внешние модули

Внешние модули находятся вне каталога ядра, обычно в:

```text
/opt/server-dashboard-extensions/<module-id>/
```

Основной конфиг только перечисляет включённые идентификаторы. Код внешнего модуля не копируется в дерево Server Dashboard и может обновляться независимо.

Модуль может:

- зарегистрировать операции чтения и изменения;
- создать отдельную страницу;
- добавить блок на главную страницу;
- добавить блок на страницу «Система»;
- подключить собственный JavaScript и CSS через зарегистрированные статические файлы.

Подробный контракт описан в [MODULE-DEVELOPMENT.md](MODULE-DEVELOPMENT.md).

## Доверие к внешнему модулю

Серверная часть модуля загружается в процесс, который работает от `root`. Поэтому внешний модуль считается доверенным кодом, а не изолированным дополнением из неизвестного источника.

Загрузчик проверяет:

- идентификатор и структуру `manifest.toml`;
- отсутствие конфликтов с уже зарегистрированными модулями и операциями;
- владельца и права файлов;
- всю цепочку родительских каталогов;
- отсутствие символических ссылок в доверенных путях;
- существование объявленных статических файлов.

Ошибка загрузки одного внешнего модуля не должна удалять уже зарегистрированные встроенные модули или операции.

## API между PHP и службой

Операции делятся на два типа:

- `read` — чтение состояния;
- `action` — изменение состояния.

Чтение идёт через `/api/rpc`, изменение — через `/api/action`. Для `/api/action` в примере Nginx используется отдельный тайм-аут, потому что перезапуск службы или контейнера может занять до минуты.

Максимальный размер ответа ограничен одновременно в Python-службе и PHP-клиенте. Ошибка преобразования ответа в JSON не завершает процесс службы, а возвращается как структурированная ошибка.

## Веб-интерфейс

Браузерная часть предоставляет объект `window.Dashboard`, который используется и встроенными страницами, и внешними модулями. Он содержит функции:

- вызова операций чтения и изменения;
- создания панелей, статусов и компактных строк;
- форматирования размера, длительности и даты;
- регистрации страницы;
- регистрации блока в поддерживаемой точке размещения.

Так внешний модуль может выглядеть как штатная часть интерфейса без копирования внутренних компонентов.

## Размещение данных

```text
/opt/server-dashboard/                 код приложения
/etc/server-dashboard/config.toml      конфигурация
/etc/server-dashboard/secrets.ini      данные входа
/opt/server-dashboard-extensions/      внешние модули
/var/log/server-dashboard/             журналы
/run/server-dashboard/                 временные файлы и Unix-сокет
```

Эта схема позволяет заменять код приложения независимо от локальной конфигурации и модулей.
